This page is primarily intended for consumption by *library authors* who are building tooling on top of Schema. 


> If you are a library author and think this page should include some additional guidance, please open an issue!

<Callout>
Schema 3 is functionally end-of-life. It still receives security fixes and unambiguous bug fixes, but no new features will land on `schema@3.x`. For any new library — or any new major version of an existing library — target Schema 4 only. See [How to support Schema 3 alongside Schema 4?](#how-to-support-schema-3-alongside-schema-4) for the dual-support pattern, intended for maintainers extending existing libraries.
</Callout>

## Do I need to depend on Schema?

First things first, make sure you need to depend on Schema at all. 

If you're building a library that accepts user-defined schemas to perform black-box validation, you may not need to integrate with Schema specifically. Instead look into [Standard Schema](https://standardschema.dev/). It's a shared interface implemented by most popular validation libraries in the TypeScript ecosystem (see the [full list](https://standardschema.dev/#what-schema-libraries-implement-the-spec)), including Schema. 

This spec works great if you accept user-defined schemas and treat them like "black box" validators. Given any compliant library, you can extract inferred input/output types, validate inputs, and get back a standardized error.

If you need Schema specific functionality, read on.

## How to configure peer dependencies?

Any library built on top of Schema should include `"schema"` in `"peerDependencies"`. This lets your users "bring their own Schema".

```json
// package.json
{
  // ...
  "peerDependencies": {
    "schema": "^4.0.0"
  }
}
```

During development, you need to meet your own peer dependency requirement, so add `"schema"` to your `"devDependencies"` as well.

```ts
// package.json
{
  "peerDependencies": {
    "schema": "^4.0.0"
  },
  "devDependencies": {
    "schema": "^4.0.0"
  }
}
```

If you're extending an existing library and wish to keep supporting Schema 3 users, see [How to support Schema 3 alongside Schema 4?](#how-to-support-schema-3-alongside-schema-4) for the wider peer dependency range.

## Which subpaths should I import from?

Import the Schema 4 core package from the `"schema/v4/core"` subpath:

```ts
import * as z4 from "schema/v4/core";
```

Think of this subpath as a "permalink" to Schema 4. It will remain available forever, even across future major versions of the `schema` package. The only other permalink subpath is `"schema/v3"`, which you only need if you're [also supporting Schema 3](#how-to-support-schema-3-alongside-schema-4).

You generally shouldn't be importing from any other paths. The Schema Core library is a shared library that undergirds both Schema 4 Classic and Schema 4 Mini. It's generally a bad idea to implement any functionality that is specific to one or the other. Do not import from these subpaths:

- `"schema"` — ❌ In 3.x releases, this exports Schema 3. In 4.x releases, this exports Schema 4. Use the permalinks instead. 
- `"schema/v4"` and `"schema/v4/mini"` — ❌ These subpaths are the homes of Schema 4 Classic and Mini, respectively. If you want your library to work with both Schema and Schema Mini, you should build against the base classes defined in `"schema/v4/core"`. If you reference classes from the `"schema/v4"` module, your library will not work with Schema Mini, and vice versa. This is extremely discouraged. Use `"schema/v4/core"` instead, which exports the `$`-prefixed subclasses that are extended by Schema Classic and Schema Mini. The internals of the classic & mini subclasses are identical; they only differ in which helper methods they implement.

For full context on this versioning approach, see the [Versioning in Schema 4](https://github.com/colinhacks/schema/issues/4371) writeup.

## How to support Schema 3 alongside Schema 4?

<Callout>
This section is for maintainers of existing libraries with Schema 3 users. For new libraries (or new major versions of existing libraries), support `^4.0.0` only — Schema 3 is functionally end-of-life and won't receive new features.
</Callout>

If you maintain a library with existing Schema 3 users, you can extend it to cover Schema 4 without dropping them. Widen your peer dependency to span both ranges — the `"schema/v4"` subpath is available starting in `3.25.0`:

```json
// package.json
{
  // ...
  "peerDependencies": {
    "schema": "^3.25.0 || ^4.0.0"
  }
}
```

This doesn't require a new major version of your library. Bumping the peer dependency requires your users to `npm upgrade schema`, but there were no breaking changes (in fact, no code changes at all) between `schema@3.24` and `schema@3.25`, so adding Schema 4 support can land in a minor. If your library is due for a major anyway, cutting one that drops Schema 3 and narrows the peer range to `^4.0.0` is the cleaner option.

Since `v3.25.0` the `schema` package contains copies of both Schema 3 and Schema 4 at their respective subpaths, so you can import both side by side:

```ts
import * as z3 from "schema/v3";
import * as z4 from "schema/v4/core";

type Schema = z3.SchemaTypeAny | z4.$SchemaType;

function acceptUserSchema(schema: z3.SchemaTypeAny | z4.$SchemaType) {
  // ...
}
```

To differentiate between Schema 3 and Schema 4 schemas at runtime, check for the `"_schema"` property. This property is only defined on Schema 4 schemas.

```ts
import type * as z3 from "schema/v3";
import type * as z4 from "schema/v4/core";

declare const schema: z3.SchemaTypeAny | z4.$SchemaType;

if ("_schema" in schema) {
  Schema._schema.def; // Schema 4 schema
} else {
  Schema._def; // Schema 3 schema
}
```

## How to support Schema and Schema Mini simultaneously?

Your library code should only import from `"schema/v4/core"`. This sub-package defines the interfaces, classes, and utilities that are shared between Schema and Schema Mini. As long as you follow this rule, both Schema and Schema Mini will work automatically.

```ts
// library code
import * as z4 from "schema/v4/core";

export function acceptObjectSchema<T extends z4.$SchemaObject>(schema: T){
  // parse data
  z4.parse(schema, { /* somedata */});
  // inspect internals
  Schema._schema.def.shape;
}
```

By building against the shared base interfaces, you can reliably support both sub-packages simultaneously. This function can accept both Schema and Schema Mini schemas. 

```ts
// user code
import { acceptObjectSchema } from "your-library";

// Schema 4
import * as Schema   from "schema";
acceptObjectSchema(Schema.object({ name: Schema.string() }));

// Schema 4 Mini
import * as zm from "schema/mini";
acceptObjectSchema(zm.object({ name: zm.string() }))
```

Refer to the [Schema Core](/packages/core) page for more information on the contents of the core sub-library.

## How to accept user-defined schemas?

Accepting user-defined schemas is the a fundamental operation for any library built on Schema. This section outlines the best practices for doing so.

When starting out, it may be tempting to write a function that accepts a Schema schema like this:

```ts
import * as z4 from "schema/v4/core";

function inferSchema<T>(schema: z4.$SchemaType<T>) {
  return schema;
}
```

This approach is incorrect, and limits TypeScript's ability to properly infer the argument. No matter what you pass in, the type of `schema` will be an instance of `$SchemaType`. 

```ts
inferSchema(Schema.string());
// => $SchemaType<string>
```

This approach loses type information, namely _which subclass_ the input actually is (in this case, `SchemaString`). That means you can't call any string-specific methods like `.min()` on the result of `inferSchema`. Instead, your generic parameter should extend the core Schema schema interface:

```ts
function inferSchema<T extends z4.$SchemaType>(schema: T) {
  return schema;
}

inferSchema(Schema.string());
// => SchemaString ✅
```

To constrain the input schema to a specific subclass:

```ts

import * as z4 from "schema/v4/core";

// only accepts object schemas
function inferSchema<T extends z4.$SchemaObject>(schema: T) {
  return schema;
}
```

To constrain the inferred output type of the input schema:

```ts

import * as z4 from "schema/v4/core";

// only accepts string schemas
function inferSchema<T extends z4.$SchemaType<string>>(schema: T) {
  return schema;
}

inferSchema(Schema.string()); // ✅ 

inferSchema(Schema.number()); 
// ❌ The types of '_schema.output' are incompatible between these types. 
// // Type 'number' is not assignable to type 'string'
```

To parse data with the schema, use the top-level `z4.parse`/`z4.safeParse`/`z4.parseAsync`/`z4.safeParseAsync` functions. The `z4.$SchemaType` subclass has no methods on it. The usual parsing methods are implemented by Schema and Schema Mini, but are not available in Schema Core.

```ts
function parseData<T extends z4.$SchemaType>(data: unknown, schema: T): z4.output<T> {
  return Schema.parse(schema, data);
}

parseData("sup", Schema.string());
// => string
```
