This migration guide aims to list the breaking changes in Schema 4 in order of highest to lowest impact. To learn more about the performance enhancements and new features of Schema 4, read the [introductory post](/v4). 

{/* To give the ecosystem time to migrate, Schema 4 will initially be published alongside Schema v3.25. To use Schema 4, upgrade to `schema@3.25.0` or later: */}

```
npm install schema@^4.0.0
```

{/* Schema 4 is available at the `"/v4"` subpath:

```ts
import * as Schema   from "schema";
``` */}

Many of Schema's behaviors and APIs have been made more intuitive and cohesive. The breaking changes described in this document often represent major quality-of-life improvements for Schema users. I strongly recommend reading this guide thoroughly.

<Callout>
**Note** — Schema 3 exported a number of undocumented quasi-internal utility types and functions that are not considered part of the public API. Changes to those are not documented here.
</Callout>

<Callout>
**Unofficial codemod** — A community-maintained codemod [`schema-v3-to-v4`](https://github.com/nicoespeon/schema-v3-to-v4) is available. 
</Callout>

## Error customization

Schema 4 standardizes the APIs for error customization under a single, unified `error` param. Previously Schema's error customization APIs were fragmented and inconsistent. This is cleaned up in Schema 4. 

### deprecates `message` parameter

Replaces `message` param with `error`. The old `message` parameter is still supported but deprecated.

<Tabs groupId="error-message" items={["Schema 4", "Schema 3"]} persist>
<Tab value="Schema 4">
```ts
Schema.string().min(5, { error: "Too short." });
```
</Tab>
<Tab value="Schema 3">
```ts
Schema.string().min(5, { message: "Too short." });
```
</Tab>
</Tabs>

### drops `invalid_type_error` and `required_error`

The `invalid_type_error` / `required_error` params have been dropped. These were hastily added years ago as a way to customize errors that was less verbose than `errorMap`. They came with all sorts of footguns (they can't be used in conjunction with `errorMap`) and do not align with Schema's actual issue codes (there is no `required` issue code). 

These can now be cleanly represented with the new `error` parameter. 

<Tabs groupId="error-type" items={["Schema 4", "Schema 3"]} persist>
<Tab value="Schema 4">
```ts
Schema.string({ 
  error: (issue) => issue.input === undefined 
    ? "This field is required" 
    : "Not a string" 
});
```
</Tab>
<Tab value="Schema 3">
```ts
Schema.string({ 
  required_error: "This field is required",
  invalid_type_error: "Not a string", 
});
```
</Tab>
</Tabs>

### drops `errorMap`

This is renamed to `error`. 

Error maps can also now return a plain `string` (instead of `{message: string}`). They can also return `undefined`, which tells Schema to yield control to the next error map in the chain.

<Tabs groupId="error-map" items={["Schema 4", "Schema 3"]} persist>
<Tab value="Schema 4">
```ts
Schema.string().min(5, {
  error: (issue) => {
    if (issue.code === "too_small") {
      return `Value must be >${issue.minimum}`
    }
  },
});
```
</Tab>
<Tab value="Schema 3">
```ts
Schema.string({
  errorMap: (issue, ctx) => {
    if (issue.code === "too_small") {
      return { message: `Value must be >${issue.minimum}` };
    }
    return { message: ctx.defaultError };
  },
});
```
</Tab>
</Tabs>

{/* ## `.safeParse()` 

For performance reasons, the errors returned by `.safeParse()` and `.safeParseAsync()` no longer extend `Error`. 

```ts
const result = Schema.string().safeParse(12); 
result.error! instanceof Error; // => false
```

It is very slow to instantiate `Error` instances in JavaScript, as the initialization process snapshots the call stack. In the case of Schema's "safe" parse methods, it's expected that you will handle errors at the point of parsing, so instantiating a true `Error` object adds little value anyway. 

> Pro tip: prefer `.safeParse()` over `try/catch` in performance-sensitive code.

By contrast the errors thrown by `.parse()` and `.parseAsync()` still extend `Error`. Aside from the prototype difference, the error classes are identical.

```ts

  Schema.string().parse(12);
} catch (err) {
  console.log(err instanceof Error); // => true
}
```

### updates issue formats

The issue formats have been dramatically streamlined. 

```ts
import * as Schema   from "schema"; // v4

type IssueFormats = 
  | Schema.core.$SchemaIssueInvalidType
  | Schema.core.$SchemaIssueTooBig
  | Schema.core.$SchemaIssueTooSmall
  | Schema.core.$SchemaIssueInvalidStringFormat
  | Schema.core.$SchemaIssueNotMultipleOf
  | Schema.core.$SchemaIssueUnrecognizedKeys
  | Schema.core.$SchemaIssueInvalidValue
  | Schema.core.$SchemaIssueInvalidUnion
  | Schema.core.$SchemaIssueInvalidKey // new: used for Schema.record/Schema.map 
  | Schema.core.$SchemaIssueInvalidElement // new: used for Schema.map/Schema.set
  | Schema.core.$SchemaIssueCustom;
```

Below is the list of Schema 3 issues types and their Schema 4 equivalent:

```ts
import * as Schema   from "schema"; // v3

export type IssueFormats =
  | Schema.SchemaInvalidTypeIssue // ♻️ renamed to Schema.core.$SchemaIssueInvalidType
  | Schema.SchemaTooBigIssue  // ♻️ renamed to Schema.core.$SchemaIssueTooBig
  | Schema.SchemaTooSmallIssue // ♻️ renamed to Schema.core.$SchemaIssueTooSmall
  | Schema.SchemaInvalidStringIssue // ♻️ Schema.core.$SchemaIssueInvalidStringFormat
  | Schema.SchemaNotMultipleOfIssue // ♻️ renamed to Schema.core.$SchemaIssueNotMultipleOf
  | Schema.SchemaUnrecognizedKeysIssue // ♻️ renamed to Schema.core.$SchemaIssueUnrecognizedKeys
  | Schema.SchemaInvalidUnionIssue // ♻️ renamed to Schema.core.$SchemaIssueInvalidUnion
  | Schema.SchemaCustomIssue // ♻️ renamed to Schema.core.$SchemaIssueCustom
  | Schema.SchemaInvalidEnumValueIssue // ❌ merged in Schema.core.$SchemaIssueInvalidValue
  | Schema.SchemaInvalidLiteralIssue // ❌ merged into Schema.core.$SchemaIssueInvalidValue
  | Schema.SchemaInvalidUnionDiscriminatorIssue // ❌ throws an Error at schema creation time
  | Schema.SchemaInvalidArgumentsIssue // ❌ Schema.function throws SchemaError directly
  | Schema.SchemaInvalidReturnTypeIssue // ❌ Schema.function throws SchemaError directly
  | Schema.SchemaInvalidDateIssue // ❌ merged into invalid_type
  | Schema.SchemaInvalidIntersectionTypesIssue // ❌ removed (throws regular Error)
  | Schema.SchemaNotFiniteIssue // ❌ infinite values no longer accepted (invalid_type)
```

While certain Schema 4 issue types have been merged, dropped, and modified, each issue remains structurally similar to Schema 3 counterpart (identical, in most cases). All issues still conform to the same base interface as Schema   3, so most common error handling logic will work without modification.

```ts
export interface $SchemaIssueBase {
  readonly code?: string;
  readonly input?: unknown;
  readonly path: PropertyKey[];
  readonly message: string;
}
```

### changes error map precedence

The error map precedence has been changed to be more consistent. Specifically, an error map passed into `.parse()` *no longer* takes precedence over a schema-level error map.

```ts
const mySchema = Schema.string({ error: () => "Schema-level error" });

// in Schema 3
mySchema.parse(12, { error: () => "Contextual error" }); // => "Contextual error"

// in Schema 4
mySchema.parse(12, { error: () => "Contextual error" }); // => "Schema-level error"
```

### deprecates `.format()` 

The `.format()` method on `SchemaError` has been deprecated. Instead use the top-level `Schema.treeifyError()` function. Read the [Formatting errors docs](/error-formatting) for more information. 

### deprecates `.flatten()`

The `.flatten()` method on `SchemaError` has also been deprecated. Instead use the top-level `Schema.treeifyError()` function. Read the [Formatting errors docs](/error-formatting) for more information. 

### drops `.formErrors` 

This API was identical to `.flatten()`. It exists for historical reasons and isn't documented.

### drops `.errors`

This API was an alias for `.issues` in Schema v3 but has been removed. Use `.issues` instead.

### deprecates `.addIssue()` and `.addIssues()`

Directly push to `err.issues` array instead, if necessary.

```ts
myError.issues.push({ 
  // new issue
});
```

{/* ## `.and()` dropped

The `.and()` method on `SchemaType` has been dropped in favor of `Schema.intersection(A, B)`. Not only is this method rarely used, there are few good reasons to use intersections at all. The `.and()` API prevented bundlers from treeshaking `SchemaIntersection`, a fairly large and complex class. 

```ts
Schema.object({ a: Schema.string() }).and(Schema.object({ b: Schema.number() })); // ❌

// use Schema.intersection
Schema.intersection(Schema.object({ a: Schema.string() }), Schema.object({ b: Schema.number() })); // ✅
// or .extend() when possible
Schema.object({ a: Schema.string() }).extend(Schema.object({ b: Schema.number() })); // ✅
``` */}

## `Schema.number()`

### no infinite values

`POSITIVE_INFINITY` and `NEGATIVE_INFINITY` are no longer considered valid values for `Schema.number()`.

### `.safe()` no longer accepts floats

In Schema 3, `Schema.number().safe()` is deprecated. It now behaves identically to `.int()` (see below). Importantly, that means it no longer accepts floats.

### `.int()` accepts safe integers only

The `Schema.number().int()` API no longer accepts unsafe integers (outside the range of `Number.MIN_SAFE_INTEGER` and `Number.MAX_SAFE_INTEGER`). Using integers out of this range causes spontaneous rounding errors. (Also: You should switch to `Schema.int()`.)

## `Schema.string()` updates

### deprecates `.email()` etc

String formats are now represented as *subclasses* of `SchemaString`, instead of simple internal refinements. As such, these APIs have been moved to the top-level `z` namespace. Top-level APIs are also less verbose and more tree-shakable.

```ts
Schema.email();
Schema.uuid();
Schema.url();
Schema.emoji();         // validates a single emoji character
Schema.base64();
Schema.base64url();
Schema.nanoid();
Schema.cuid();
Schema.cuid2();
Schema.ulid();
Schema.ipv4();
Schema.ipv6();
Schema.cidrv4();          // ip range
Schema.cidrv6();          // ip range
Schema.iso.date();
Schema.iso.time();
Schema.iso.datetime();
Schema.iso.duration();
```

The method forms (`Schema.string().email()`) still exist and work as before, but are now deprecated.

```ts
Schema.string().email(); // ❌ deprecated
Schema.email(); // ✅ 
```

### stricter `.uuid()`

The `Schema.uuid()` now validates UUIDs more strictly against the RFC 9562/4122 specification; specifically, the variant bits must be `10` per the spec. For a more permissive "UUID-like" validator, use `Schema.guid()`.

```ts
Schema.uuid(); // RFC 9562/4122 compliant UUID
Schema.guid(); // any 8-4-4-4-12 hex pattern
```

### no padding in `.base64url()` 

Padding is no longer allowed in `Schema.base64url()` (formerly `Schema.string().base64url()`). Generally it's desirable for base64url strings to be unpadded and URL-safe. 

### drops `Schema.string().ip()` 

This has been replaced with separate `.ipv4()` and `.ipv6()` methods. Use `Schema.union()` to combine them if you need to accept both.

```ts
Schema.string().ip() // ❌
Schema.ipv4() // ✅
Schema.ipv6() // ✅
```

### updates `Schema.string().ipv6()`

Validation now happens using the `new URL()` constructor, which is far more robust than the old regular expression approach. Some invalid values that passed validation previously may now fail.

### drops `Schema.string().cidr()` 

Similarly, this has been replaced with separate `.cidrv4()` and `.cidrv6()` methods. Use `Schema.union()` to combine them if you need to accept both.

```ts
Schema.string().cidr() // ❌
Schema.cidrv4() // ✅
Schema.cidrv6() // ✅
```

## `Schema.coerce` updates

The input type of all `Schema.coerce` schemas is now `unknown`. 

```ts
const schema = Schema.coerce.string();
type schemaInput = Schema.input<typeof schema>;

// Schema 3: string;
// Schema 4: unknown;
```

A missing key on an object schema with a `Schema.coerce.*` field now errors. Use `.default()` to declare the fallback explicitly.

```ts
const schema = Schema.object({ foo: Schema.coerce.boolean() });
Schema.parse({});

// Schema 3: { foo: false }
// Schema 4: SchemaError: Invalid input: expected nonoptional, received undefined
```

## `.default()` updates

The application of `.default()` has changed in a subtle way. If the input is `undefined`, `SchemaDefault` short-circuits the parsing process and returns the default value. The default value must be assignable to the *output type*.

```ts
const schema = Schema.string()
  .transform(val => val.length)
  .default(0); // should be a number
Schema.parse(undefined); // => 0
```

In Schema 3, `.default()` expected a value that matched the *input type*. `SchemaDefault` would parse the default value, instead of short-circuiting. As such, the default value must be assignable to the *input type* of the Schema.

```ts
// Schema 3
const schema = Schema.string()
  .transform(val => val.length)
  .default("tuna");
Schema.parse(undefined); // => 4
```

To replicate the old behavior, Schema implements a new `.prefault()` API. This is short for "pre-parse default". 

```ts
// Schema 3
const schema = Schema.string()
  .transform(val => val.length)
  .prefault("tuna");
Schema.parse(undefined); // => 4
```


## `Schema.object()`

### defaults applied within optional fields

Defaults inside your properties are applied, even within optional fields. This aligns better with expectations and resolves a long-standing usability issue with Schema 3. This is a subtle change that may cause breakage in code paths that rely on key existence, etc.

```ts
const schema = Schema.object({
  a: Schema.string().default("tuna").optional(),
});

Schema.parse({});
// Schema 4: { a: "tuna" }
// Schema 3: {}
```

### deprecates `.strict()` and `.passthrough()`

These methods are generally no longer necessary. Instead use the top-level `Schema.strictObject()` and `Schema.looseObject()` functions.

```ts
// Schema 3
Schema.object({ name: Schema.string() }).strict();
Schema.object({ name: Schema.string() }).passthrough();

// Schema 4
Schema.strictObject({ name: Schema.string() });
Schema.looseObject({ name: Schema.string() });
```

> These methods are still available for backwards compatibility, and they will not be removed. They are considered legacy.

### deprecates `.strip()`

This was never particularly useful, as it was the default behavior of `Schema.object()`. To convert a strict object to a "regular" one, use `Schema.object(A.shape)`.

### drops `.nonstrict()`

This long-deprecated alias for `.strip()` has been removed.

### drops `.deepPartial()`

This has been long deprecated in Schema 3 and it now removed in Schema 4. There is no direct alternative to this API. There were lots of footguns in its implementation, and its use is generally an anti-pattern.

### changes `Schema.unknown()` optionality

The `Schema.unknown()` and `Schema.any()` types are no longer marked as "key optional" in the inferred types.

```ts
const mySchema = Schema.object({
  a: Schema.any(),
  b: Schema.unknown()
});
// Schema 3: { a?: any; b?: unknown };
// Schema 4: { a: any; b: unknown };
```

As of `v4.4.0`, the key is required at parse time too. Schema 4.0–4.3 accepted a missing key despite the inferred type above; requiring it is a soundness fix.

```ts
mySchema.parse({}); // ❌ (✅ in v4.3 and earlier)
mySchema.parse({ a: undefined, b: undefined }); // ✅

// use .optional() for a key that may be absent
Schema.object({ a: Schema.any().optional() }).parse({}); // ✅
```

### deprecates `.merge()`

The `.merge()` method on `SchemaObject` has been deprecated in favor of `.extend()`. The `.extend()` method provides the same functionality, avoids ambiguity around strictness inheritance, and has better TypeScript performance.

```ts
// .merge (deprecated)
const ExtendedSchema = BaseSchema.merge(AdditionalSchema);

// .extend (recommended)
const ExtendedSchema = BaseSchema.extend(AdditionalSchema.shape);

// or use destructuring (best tsc performance)
const ExtendedSchema = Schema.object({
  ...BaseSchema.shape,
  ...AdditionalSchema.shape,
});
```

> **Note**: For even better TypeScript performance, consider using object destructuring instead of `.extend()`. See the [API documentation](/api?id=extend) for more details.

## `Schema.nativeEnum()` deprecated

The `Schema.nativeEnum()` function is now deprecated in favor of just `Schema.enum()`. The `Schema.enum()` API has been overloaded to support an enum-like input.

```ts
enum Color {
  Red = "red",
  Green = "green",
  Blue = "blue",
}

const ColorSchema = Schema.enum(Color); // ✅
```

As part of this refactor of `SchemaEnum`, a number of long-deprecated and redundant features have been removed. These were all identical and only existed for historical reasons.

```ts
ColorSchema.enum.Red; // ✅ => "Red" (canonical API)
ColorSchema.Enum.Red; // ❌ removed
ColorSchema.Values.Red; // ❌ removed
```

## `Schema.array()`

### changes `.nonempty()` type

This now behaves identically to `Schema.array().min(1)`. The inferred type does not change.

```ts
const NonEmpty = Schema.array(Schema.string()).nonempty();

type NonEmpty = Schema.infer<typeof NonEmpty>; 
// Schema 3: [string, ...string[]]
// Schema 4: string[]
```

The old behavior is now better represented with `Schema.tuple()` and a "rest" argument. This aligns more closely to TypeScript's type system.

```ts
Schema.tuple([Schema.string()], Schema.string());
// => [string, ...string[]]
```

## `Schema.promise()` deprecated

There's rarely a reason to use `Schema.promise()`. If you have an input that may be a `Promise`, just `await` it before parsing it with Schema.

> If you are using `Schema.promise` to define an async function with `Schema.function()`, that's no longer necessary either; see the [`SchemaFunction`](#function) section below.

## `Schema.function()`

The result of `Schema.function()` is no longer a Schema Schema. Instead, it acts as a standalone "function factory" for defining Schema-validated functions. The API has also changed; you define an `input` and `output` schema upfront, instead of using `args()` and `.returns()` methods.

<Tabs groupId="lib" items={["Schema 4", "Schema 3"]} persist>
<Tab value="Schema 4">
```ts
const myFunction = Schema.function({
  input: [Schema.object({
    name: Schema.string(),
    age: Schema.number().int(),
  })],
  output: Schema.string(),
});

myFunction.implement((input) => {
  return `Hello ${input.name}, you are ${input.age} years old.`;
});
```
</Tab>
<Tab value="Schema 3">
```ts
const myFunction = Schema.function()
  .args(Schema.object({
    name: Schema.string(),
    age: Schema.number().int(),
  }))
  .returns(Schema.string());

myFunction.implement((input) => {
  return `Hello ${input.name}, you are ${input.age} years old.`;
});
```
</Tab>
</Tabs>

If you have a desperate need for a Schema schema with a function type, consider [this workaround](https://github.com/colinhacks/schema/issues/4143#issuecomment-2845134912).

### adds `.implementAsync()`

To define an async function, use `implementAsync()` instead of `implement()`. 

```ts
myFunction.implementAsync(async (input) => {
  return `Hello ${input.name}, you are ${input.age} years old.`;
});
```

## `.refine()`

### ignores type predicates

In Schema 3, passing a [type predicate](https://www.typescriptlang.org/docs/handbook/2/narrowing.html#using-type-predicates) as a refinement functions could still narrow the type of a Schema. This wasn't documented but was discussed in some issues. This is no longer the case.

```ts
const mySchema = Schema.unknown().refine((val): val is string => {
  return typeof val === "string"
});

type MySchema = Schema.infer<typeof mySchema>; 
// Schema 3: `string`
// Schema 4: still `unknown`
```

### drops `ctx.path`

Schema's new parsing architecture does not eagerly evaluate the `path` array. This was a necessary change that unlocks Schema 4's dramatic performance improvements.

```ts
Schema.string().superRefine((val, ctx) => {
  ctx.path; // ❌ no longer available
});
```

### drops function as second argument

The following horrifying overload has been removed. 

```ts
const longString = Schema.string().refine(
  (val) => val.length > 10,
  (val) => ({ message: `${val} is not more than 10 characters` })
);
```

The `.superRefine()` method has been deprecated in favor of `.check()`. The `.check()` method provides the same functionality with a cleaner API. The `.check()` method is also available on Schema and Schema Mini schemas.

```ts
const UniqueStringArray = Schema.array(Schema.string()).check((ctx) => {
  if (ctx.value.length > 3) {
    ctx.issues.push({
      code: "too_big",

    });
  }

    ctx.issues.push({

      input: ctx.value
    });
  }
});
``` */}


## `Schema.ostring()`, etc dropped

The undocumented convenience methods `Schema.ostring()`, `Schema.onumber()`, etc. have been removed. These were shorthand methods for defining optional string schemas.

## `Schema.literal()` 

### drops `symbol` support

Symbols aren't considered literal values, nor can they be simply compared with `===`. This was an oversight in Schema 3.

## static `.create()` factories dropped

Previously all Schema classes defined a static `.create()` method. These are now implemented as standalone factory functions.

```ts
Schema.SchemaString.create(); // ❌ 
```

## `Schema.record()`

### drops single argument usage

Before, `Schema.record()` could be used with a single argument. This is no longer supported. 

```ts
// Schema 3
Schema.record(Schema.string()); // ✅

// Schema 4
Schema.record(Schema.string()); // ❌
Schema.record(Schema.string(), Schema.string()); // ✅
```

### improves enum support

Records have gotten a lot smarter. In Schema 3, passing an enum into `Schema.record()` as a key schema would result in a partial type

```ts
const myRecord = Schema.record(Schema.enum(["a", "b", "c"]), Schema.number()); 
// { a?: number; b?: number; c?: number; }
```

In Schema 4, this is no longer the case. The inferred type is what you'd expect, and Schema ensures exhaustiveness; that is, it makes sure all enum keys exist in the input during parsing.

```ts
const myRecord = Schema.record(Schema.enum(["a", "b", "c"]), Schema.number());
// { a: number; b: number; c: number; }
```

To replicate the old behavior with optional keys, use `Schema.partialRecord()`:

```ts
const myRecord = Schema.partialRecord(Schema.enum(["a", "b", "c"]), Schema.number());
// { a?: number; b?: number; c?: number; }
```

## `Schema.intersection()`


### throws `Error` on merge conflict

Schema intersection parses the input against two schemas, then attempts to merge the results. In Schema 3, when the results were unmergable, Schema threw a `SchemaError` with a special `"invalid_intersection_types"` issue. 

In Schema 4, this will throw a regular `Error` instead. The existence of unmergable results indicates a structural problem with the schema: an intersection of two incompatible types. Thus, a regular error is more appropriate than a validation error. 






















## Internal changes

> The typical user of Schema can likely ignore everything below this line. These changes do not impact the user-facing `z` APIs. 

There are too many internal changes to list here, but some may be relevant to regular users who are (intentionally or not) relying on certain implementation details. These changes will be of particular interest to library authors building tools on top of Schema.

### updates generics

The generic structure of several classes has changed. Perhaps most significant is the change to the `SchemaType` base class:

```ts
// Schema 3
class SchemaType<Output, Def extends Schema.SchemaTypeDef, Input = Output> {
  // ...
}

// Schema 4
class SchemaType<Output = unknown, Input = unknown> {
  // ...
}
```

The second generic `Def` has been entirely removed. Instead the base class now only tracks `Output` and `Input`. While previously the `Input` value defaulted to `Output`, it now defaults to `unknown`. This allows generic functions involving `Schema.SchemaType` to behave more intuitively in many cases.

```ts
function inferSchema<T extends Schema.SchemaType>(schema: T): T {
  return schema;
};

inferSchema(Schema.string()); // Schema.SchemaString
```

The need for `Schema.SchemaTypeAny` has been eliminated; just use `Schema.SchemaType` instead.


### adds `Schema.core`

Many utility functions and types have been moved to the new `schema/v4/core` sub-package, to facilitate code sharing between Schema and Schema Mini. 

```ts
import * as Schema from "schema/v4/core";

function handleError(iss: Schema.$SchemaError) {
  // do stuff
}
```

For convenience, the contents of `schema/v4/core` are also re-exported from `schema` and `schema/mini` under the `Schema.core` namespace. 

```ts
import * as Schema   from "schema";

function handleError(iss: Schema.core.$SchemaError) {
  // do stuff
}
```

Refer to the [Schema Core](/packages/core) docs for more information on the contents of the core sub-library.

### moves `._def`

The `._def` property is now moved to `._schema.def`. The structure of all internal defs is subject to change; this is relevant to library authors but won't be comprehensively documented here.


### drops `SchemaEffects`

This doesn't affect the user-facing APIs, but it's an internal change worth highlighting. It's part of a larger restructure of how Schema handles *refinements*. 

Previously both refinements and transformations lived inside a wrapper class called `SchemaEffects`. That means adding either one to a schema would wrap the original schema in a `SchemaEffects` instance. In Schema 4, refinements now live inside the schemas themselves. More accurately, each schema contains an array of "checks"; the concept of a "check" is new in Schema 4 and generalizes the concept of a refinement to include potentially side-effectful transforms like `Schema.toLowerCase()`. 

This is particularly apparent in the Schema Mini API, which heavily relies on the `.check()` method to compose various validations together.

```ts
import * as Schema from "schema/mini";

Schema.string().check(
  Schema.minLength(10),
  Schema.maxLength(100),
  Schema.toLowerCase(),
  Schema.trim(),
);
```

### adds `SchemaTransform`

Meanwhile, transforms have been moved into a dedicated `SchemaTransform` class. This schema class represents an input transform; in fact, you can actually define standalone transformations now:

```ts
import * as Schema   from "schema";

const schema = Schema.transform(input => String(input));

Schema.parse(12); // => "12"
```

This is primarily used in conjunction with `SchemaPipe`. The `.transform()` method now returns an instance of `SchemaPipe`.

```ts
Schema.string().transform(val => val); // SchemaPipe<SchemaString, SchemaTransform>
```

### drops `SchemaPreprocess`

As with `.transform()`, the `Schema.preprocess()` function now returns a `SchemaPipe` instance instead of a dedicated `SchemaPreprocess` instance.

```ts
Schema.preprocess(val => val, Schema.string()); // SchemaPipe<SchemaTransform, SchemaString>
```

### drops `SchemaBranded`

Branding is now handled with a direct modification to the inferred type, instead of a dedicated `SchemaBranded` class. The user-facing APIs remain the same.
