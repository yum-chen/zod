## Why a new major version?

Schema v3.0 was released in May 2021 (!). Back then Schema had 2700 stars on GitHub and 600k weekly downloads. Today it has 37.8k stars and 31M weekly downloads (up from 23M when the beta came out 6 weeks ago!). After 24 minor versions, the Schema 3 codebase had hit a ceiling; the most commonly requested features and improvements require breaking changes.

Schema 4 fixes a number of long-standing design limitations of Schema 3 in one fell swoop, paving the way for several long-requested features and a huge leap in performance. It closes 9 of Schema's [10 most upvoted open issues](https://github.com/colinhacks/schema/issues?q=is%3Aissue%20state%3Aopen%20sort%3Areactions-%2B1-desc). With luck, it will serve as the new foundation for many more years to come.

For a scannable breakdown of what's new, see the table of contents. Click on any item to jump to that section.

## 100x reduction in `tsc` instantiations

Consider the following simple file:

```ts
import * as Schema   from "schema";

export const A = Schema.object({
  a: Schema.string(),
  b: Schema.string(),
  c: Schema.string(),
  d: Schema.string(),
  e: Schema.string(),
});

export const B = A.extend({
  f: Schema.string(),
  g: Schema.string(),
  h: Schema.string(),
});
```

Compiling this file with `tsc --extendedDiagnostics` using `"schema/v3"` results in >25000 type instantiations. With `"schema/v4"` it only results in ~175. 

<Callout>

The Schema repo contains a `tsc` benchmarking playground. Try this for yourself using the compiler benchmarks in `packages/tsc`. The exact numbers may change as the implementation evolves. 

```sh
$ cd packages/tsc
$ nub run bench object-with-extend
```
</Callout>

## 2x reduction in core bundle size

Consider the following simple script.

```ts
import * as Schema   from "schema";

const schema = Schema.boolean();

Schema.parse(true);
```

It's about as simple as it gets when it comes to validation. That's intentional; it's a good way to measure the *core bundle size*—the code that will end up in the bundle even in simple cases. We'll bundle this with `rollup` using both Schema 3 and Schema 4 and compare the final bundles. 

| Package | Bundle (gzip) |
|---------|--------------|
| Schema 3   | `12.47kb`      |
| Schema 4   | `5.36kb`       |

The core bundle is ~57% smaller in Schema 4 (2.3x). That's good! But we can do a lot better.

## Introducing Schema Mini

Schema's method-heavy API is fundamentally difficult to tree-shake. Even our simple `Schema.boolean()` script pulls in the implementations of a bunch of methods we didn't use, like `.optional()`, `.array()`, etc. Writing slimmer implementations can only get you so far. That's where Schema Mini comes in. 

```sh
npm install schema@^4.0.0
```

It's a Schema variant with a functional, tree-shakable API that corresponds one-to-one with `schema`. Where Schema uses methods, Schema Mini generally uses wrapper functions:

<Tabs groupId="lib" items={[ "Schema Mini", "Schema"]}>
<Tab value="Schema Mini">
```ts
import * as Schema from "schema/mini";

Schema.optional(Schema.string());

Schema.union([Schema.string(), Schema.number()]);

Schema.extend(Schema.object({ /* ... */ }), { age: Schema.number() });
```
</Tab>
<Tab value="Schema">
```ts
import * as Schema   from "schema";

Schema.string().optional();

Schema.string().or(Schema.number());

Schema.object({ /* ... */ }).extend({ age: Schema.number() });
```
</Tab>
</Tabs>

Not all methods are gone! The parsing methods are identical in Schema and Schema Mini:

```ts
import * as Schema from "schema/mini";

Schema.string().parse("asdf");
Schema.string().safeParse("asdf");
await Schema.string().parseAsync("asdf");
await Schema.string().safeParseAsync("asdf");
```

There's also a general-purpose `.check()` method used to add refinements.

<Tabs groupId="lib" items={[ "Schema Mini", "Schema"]}>
<Tab value="Schema Mini">
```ts
import * as Schema from "schema/mini";

Schema.array(Schema.number()).check(
  Schema.minLength(5), 
  Schema.maxLength(10),
  Schema.refine(arr => arr.includes(5))
);
```
</Tab>
<Tab value="Schema">
```ts
import * as Schema   from "schema";

Schema.array(Schema.number())
  .min(5)
  .max(10)
  .refine(arr => arr.includes(5));
```
</Tab>
</Tabs>

The following top-level refinements are available in Schema Mini. It should be fairly self-explanatory which Schema methods they correspond to.

```ts
import * as Schema from "schema/mini";

// custom checks
Schema.refine();

// first-class checks
Schema.lt(value);
Schema.lte(value); // alias: Schema.maximum()
Schema.gt(value);
Schema.gte(value); // alias: Schema.minimum()
Schema.positive();
Schema.negative();
Schema.nonpositive();
Schema.nonnegative();
Schema.multipleOf(value);
Schema.maxSize(value);
Schema.minSize(value);
Schema.size(value);
Schema.maxLength(value);
Schema.minLength(value);
Schema.length(value);
Schema.regex(regex);
Schema.lowercase();
Schema.uppercase();
Schema.includes(value);
Schema.startsWith(value);
Schema.endsWith(value);
Schema.property(key, schema); // for object schemas; check `input[key]` against `schema`
Schema.mime(value); // for file schemas (see below)

// overwrites (these *do not* change the inferred type!)
Schema.overwrite(value => newValue);
Schema.normalize();
Schema.trim();
Schema.toLowerCase();
Schema.toUpperCase();
```


This more functional API makes it easier for bundlers to tree-shake the APIs you don't use. While regular Schema is still recommended for the majority of use cases, any projects with uncommonly strict bundle size constraints should consider Schema Mini.

## Metadata

Schema 4 introduces a new system for adding strongly-typed metadata to your schemas. Metadata isn't stored inside the schema itself; instead it's stored in a "schema registry" that associates a schema with some typed metadata. To create a registry with `Schema.registry()`:

```ts
import * as Schema   from "schema";

const myRegistry = Schema.registry<{ title: string; description: string }>();
```

To add schemas to your registry: 

```ts
const emailSchema = Schema.string().email();

myRegistry.add(emailSchema, { title: "Email address", description: "..." });
myRegistry.get(emailSchema);
// => { title: "Email address", ... }
```

Alternatively, you can use the `.register()` method on a schema for convenience:

{/* > Unlike all other Schema methods, `.register()` is *not* immutable, it returns the original Schema. */}

```ts
emailSchema.register(myRegistry, { title: "Email address", description: "..." })
// => returns emailSchema
```

### The global registry

Schema also exports a global registry `Schema.globalRegistry` that accepts some common JSON Schema-compatible metadata:

```ts
Schema.globalRegistry.add(Schema.string(), { 
  id: "email_address",
  title: "Email address",
  description: "Provide your email",
  examples: ["naomie@example.com"],
  extraKey: "Additional properties are also allowed"
});
```

### `.meta()`

To conveniently add a schema to `Schema.globalRegistry`, use the `.meta()` method.

{/* > Unlike `.register()`, `.meta()` *is* immutable; it returns a new instance (a clone of the original schema). */}

```ts
Schema.string().meta({ 
  id: "email_address",
  title: "Email address",
  description: "Provide your email",
  examples: ["naomie@example.com"],
  // ...
});
```

<Callout>
For compatibility with Schema 3, `.describe()` is still available, but `.meta()` is preferred.

```ts
Schema.string().describe("An email address");

// equivalent to
Schema.string().meta({ description: "An email address" });
```
</Callout>

## JSON Schema conversion

Schema 4 introduces first-party JSON Schema conversion via `Schema.toJSONSchema()`.

```ts
import * as Schema   from "schema";

const mySchema = Schema.object({name: Schema.string(), points: Schema.number()});

Schema.toJSONSchema(mySchema);
// => {
//   type: "object",
//   properties: {
//     name: {type: "string"},
//     points: {type: "number"},
//   },
//   required: ["name", "points"],
// }
```

Any metadata in `Schema.globalRegistry` is automatically included in the JSON Schema output.

```ts
const mySchema = Schema.object({
  firstName: Schema.string().describe("Your first name"),
  lastName: Schema.string().meta({ title: "last_name" }),
  age: Schema.number().meta({ examples: [12, 99] }),
});

Schema.toJSONSchema(mySchema);
// => {
//   type: 'object',
//   properties: {
//     firstName: { type: 'string', description: 'Your first name' },
//     lastName: { type: 'string', title: 'last_name' },
//     age: { type: 'number', examples: [ 12, 99 ] }
//   },
//   required: [ 'firstName', 'lastName', 'age' ]
// }

```

Refer to the [JSON Schema docs](/json-schema) for information on customizing the generated JSON Schema.

## Recursive objects

This was an unexpected one. After years of trying to crack this problem, I finally [found a way](https://x.com/colinhacks/status/1919286275133378670) to properly infer recursive object types in Schema. To define a recursive type:

```ts
const Category = Schema.object({
  name: Schema.string(),
  get subcategories(){
    return Schema.array(Category)
  }
});

type Category = Schema.infer<typeof Category>;
// { name: string; subcategories: Category[] }
```

You can also represent *mutually recursive types*:

```ts
const User = Schema.object({
  email: Schema.email(),
  get posts(){
    return Schema.array(Post)
  }
});

const Post = Schema.object({
  title: Schema.string(),
  get author(){
    return User
  }
});
```

Unlike the Schema 3 pattern for recursive types, there's no type casting required. The resulting schemas are plain `SchemaObject` instances and have the full set of methods available. 

```ts
Post.pick({ title: true })
Post.partial();
Post.extend({ publishDate: Schema.date() });
```

## Error pretty-printing

The popularity of the [`schema-validation-error`](https://www.npmjs.com/package/schema-validation-error) package demonstrates that there's significant demand for an official API for pretty-printing errors. If you are using that package currently, by all means continue using it. 

Schema now implements a top-level `Schema.prettifyError` function for converting a `SchemaError` to a user-friendly formatted string.

```ts
const myError = new Schema.SchemaError([
  {
    code: 'unrecognized_keys',
    keys: [ 'extraField' ],
    path: [],
    message: 'Unrecognized key: "extraField"'
  },
  {
    expected: 'string',
    code: 'invalid_type',
    path: [ 'username' ],
    message: 'Invalid input: expected string, received number'
  },
  {
    origin: 'number',
    code: 'too_small',
    minimum: 0,
    inclusive: true,
    path: [ 'favoriteNumbers', 1 ],
    message: 'Too small: expected number to be >=0'
  }
]);

Schema.prettifyError(myError);
```

This returns the following pretty-printable multi-line string:

```ts
✖ Unrecognized key: "extraField"
✖ Invalid input: expected string, received number
  → at username
✖ Invalid input: expected number, received string
  → at favoriteNumbers[1]
```

Currently the formatting isn't configurable; this may change in the future.

### Custom email regex

The `Schema.email()` API now supports a custom regular expression. There is no one canonical email regex; different applications may choose to be more or less strict. For convenience Schema exports some common ones.

```ts
// Schema's default email regex (Gmail rules)
// see colinhacks.com/essays/reasonable-email-regex
Schema.email(); // Schema.regexes.email

// the regex used by browsers to validate input[type=email] fields
// https://developer.mozilla.org/en-US/docs/Web/HTML/Element/input/email
Schema.email({ pattern: Schema.regexes.html5Email });

// the classic emailregex.com regex (RFC 5322)
Schema.email({ pattern: Schema.regexes.rfc5322Email });

// a loose regex that allows Unicode (good for intl emails)
Schema.email({ pattern: Schema.regexes.unicodeEmail });
```

## Template literal types

Schema 4 implements `Schema.templateLiteral()`. Template literal types are perhaps the biggest feature of TypeScript's type system that wasn't previously representable.


```ts
const hello = Schema.templateLiteral(["hello, ", Schema.string()]);
// `hello, ${string}`

const cssUnits = Schema.enum(["px", "em", "rem", "%"]);
const css = Schema.templateLiteral([Schema.number(), cssUnits]);
// `${number}px` | `${number}em` | `${number}rem` | `${number}%`

const email = Schema.templateLiteral([
  Schema.string().min(1),
  "@",
  Schema.string().max(64),
]);
// `${string}@${string}` (the min/max refinements are enforced!)
```

Every Schema schema type that can be stringified stores an internal regex: strings, string formats like `Schema.email()`, numbers, boolean, bigint, enums, literals, undefined/optional, null/nullable, and other template literals. The `Schema.templateLiteral` constructor concatenates these into a super-regex, so things like string formats (`Schema.email()`) are properly enforced (but custom refinements are not!).

Read the [template literal docs](/api#template-literals) for more info.

## Number formats

New numeric "formats" have been added for representing fixed-width integer and float types. These return a `SchemaNumber` instance with proper inclusive minimum/maximum constraints already added.

```ts
Schema.int();      // [Number.MIN_SAFE_INTEGER, Number.MAX_SAFE_INTEGER]
Schema.float32();  // [-3.4028234663852886e38, 3.4028234663852886e38]
Schema.float64();  // [-1.7976931348623157e308, 1.7976931348623157e308]
Schema.int32();    // [-2147483648, 2147483647]
Schema.uint32();   // [0, 4294967295]
```

Similarly the following `bigint` numeric formats have also been added. These integer types exceed what can be safely represented by a `number` in JavaScript, so these return a `SchemaBigInt` instance with the proper inclusive minimum/maximum constraints already added.

```ts
Schema.int64();    // [-9223372036854775808n, 9223372036854775807n]
Schema.uint64();   // [0n, 18446744073709551615n]
```

## Stringbool

The existing `Schema.coerce.boolean()` API is very simple: falsy values (`false`, `undefined`, `null`, `0`, `""`, `NaN` etc) become `false`, truthy values become `true`.

This is still a good API, and its behavior aligns with the other `Schema.coerce` APIs. But some users requested a more sophisticated "env-style" boolean coercion. To support this, Schema 4 introduces `Schema.stringbool()`:

```ts
const strbool = Schema.stringbool();

strbool.parse("true")         // => true
strbool.parse("1")            // => true
strbool.parse("yes")          // => true
strbool.parse("on")           // => true
strbool.parse("y")            // => true
strbool.parse("enabled")      // => true

strbool.parse("false");       // => false
strbool.parse("0");           // => false
strbool.parse("no");          // => false
strbool.parse("off");         // => false
strbool.parse("n");           // => false
strbool.parse("disabled");    // => false

strbool.parse(/* anything else */); // SchemaError<[{ code: "invalid_value" }]>
```

To customize the truthy and falsy values:

```ts
Schema.stringbool({
  truthy: ["yes", "true"],
  falsy: ["no", "false"]
})
```

Refer to the [`Schema.stringbool()` docs](/api#stringbool) for more information.

## Simplified error customization

The majority of breaking changes in Schema 4 involve the *error customization* APIs. They were a bit of a mess in Schema 3; Schema 4 makes things significantly more elegant, to the point where I think it's worth highlighting here. 

Long story short, there is now a single, unified `error` parameter for customizing errors, replacing the following APIs:

Replace `message` with `error`. (The `message` parameter is still supported but deprecated.)

```diff
- Schema.string().min(5, { message: "Too short." });
+ Schema.string().min(5, { error: "Too short." });
```

Replace `invalid_type_error` and `required_error` with `error` (function syntax):

```diff
// Schema 3
- Schema.string({ 
-   required_error: "This field is required" 
-   invalid_type_error: "Not a string", 
- });

// Schema 4 
+ Schema.string({ error: (issue) => issue.input === undefined ? 
+  "This field is required" :
+  "Not a string" 
+ });
```

Replace `errorMap` with `error` (function syntax):

```diff
// Schema 3 
- Schema.string({
-   errorMap: (issue, ctx) => {
-     if (issue.code === "too_small") {
-       return { message: `Value must be >${issue.minimum}` };
-     }
-     return { message: ctx.defaultError };
-   },
- });

// Schema 4
+ Schema.string({
+   error: (issue) => {
+     if (issue.code === "too_small") {
+       return `Value must be >${issue.minimum}`
+     }
+   },
+ });
```

## Upgraded `Schema.discriminatedUnion()`

Discriminated unions now support a number of schema types not previously supported, including unions and pipes:

```ts
const MyResult = Schema.discriminatedUnion("status", [
  // simple literal
  Schema.object({ status: Schema.literal("aaa"), data: Schema.string() }),
  // union discriminator
  Schema.object({ status: Schema.union([Schema.literal("bbb"), Schema.literal("ccc")]) }),
  // pipe discriminator
  Schema.object({ status: Schema.literal("fail").transform(val => val.toUpperCase()) }),
]);
```

Perhaps most importantly, discriminated unions now *compose*—you can use one discriminated union as a member of another.

```ts
const BaseError = Schema.object({ status: Schema.literal("failed"), message: Schema.string() });

const MyResult = Schema.discriminatedUnion("status", [
  Schema.object({ status: Schema.literal("success"), data: Schema.string() }),
  Schema.discriminatedUnion("code", [
    BaseError.extend({ code: Schema.literal(400) }),
    BaseError.extend({ code: Schema.literal(401) }),
    BaseError.extend({ code: Schema.literal(500) })
  ])
]);
```

## Multiple values in `Schema.literal()`

The `Schema.literal()` API now optionally supports multiple values. 

```ts
const httpCodes = Schema.literal([ 200, 201, 202, 204, 206, 207, 208, 226 ]);

// previously in Schema 3:
const httpCodes = Schema.union([
  Schema.literal(200),
  Schema.literal(201),
  Schema.literal(202),
  Schema.literal(204),
  Schema.literal(206),
  Schema.literal(207),
  Schema.literal(208),
  Schema.literal(226)
]);
```

## Refinements live inside schemas

In Schema 3, they were stored in a `SchemaEffects` class that wrapped the original Schema. This was inconvenient, as it meant you couldn't interleave `.refine()` with other schema methods like `.min()`.

```ts
Schema.string()
  .refine(val => val.includes("@"))
  .min(5);
// ^ ❌ Property 'min' does not exist on type SchemaEffects<SchemaString, string, string>
```

In Schema 4, refinements are stored inside the schemas themselves, so the code above works as expected.

```ts
Schema.string()
  .refine(val => val.includes("@"))
  .min(5); // ✅
```

### `.overwrite()`

The `.transform()` method is extremely useful, but it has one major downside: the output type is no longer *introspectable* at runtime. The transform function is a black box that can return anything. This means (among other things) there's no sound way to convert the schema to JSON Schema.

```ts
const Squared = Schema.number().transform(val => val ** 2);
// => SchemaPipe<SchemaNumber, SchemaTransform>
```

Schema 4 introduces a new `.overwrite()` method for representing transforms that *don't change the inferred type*. Unlike `.transform()`, this method returns an instance of the original class. The overwrite function is stored as a refinement, so it doesn't (and can't) modify the inferred type.

```ts
Schema.number().overwrite(val => val ** 2).max(100);
// => SchemaNumber
```

> The existing `.trim()`, `.toLowerCase()` and `.toUpperCase()` methods have been reimplemented using `.overwrite()`.

## An extensible foundation: `schema/v4/core`

While this will not be relevant to the majority of Schema users, it's worth highlighting. The addition of Schema Mini necessitated the creation of a shared sub-package `schema/v4/core` which contains the core functionality shared between Schema and Schema Mini. 

I was resistant to this at first, but now I see it as one of Schema 4's most important features. It lets Schema level up from a simple library to a fast validation "substrate" that can be sprinkled into other libraries.

If you're building a schema library, refer to the implementations of Schema and Schema Mini to see how to build on top of the foundation `schema/v4/core` provides.
