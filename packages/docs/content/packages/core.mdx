This sub-package exports the core classes and utilities that are consumed by Schema and Schema Mini. It is not intended to be used directly; instead it's designed to be extended by other packages. It implements:

```ts
import * as Schema from "schema/v4/core";

// the base class for all Schema schemas
Schema.$SchemaType;

// subclasses of $SchemaType that implement common parsers
Schema.$SchemaString
Schema.$SchemaObject
Schema.$SchemaArray
// ...

// the base class for all Schema checks
Schema.$SchemaCheck;

// subclasses of $SchemaCheck that implement common checks
Schema.$SchemaCheckMinLength
Schema.$SchemaCheckMaxLength

// the base class for all Schema errors
Schema.$SchemaError;

// issue formats (types only)
{} as Schema  .$SchemaIssue;

// utils
Schema.util.isValidJWT(...);
```

## Schemas

The base class for all Schema schemas is `$SchemaType`. It accepts two generic parameters: `Output` and `Input`.

```ts
export class $SchemaType<Output = unknown, Input = unknown> {
  _schema: { /* internals */}
}
```

`schema/v4/core` exports a number of subclasses that implement some common parsers. A union of all first-party subclasses is exported as `Schema.$SchemaTypes`.

## Internals

All `schema/v4/core` subclasses only contain a single property: `_schema`. This property is an object containing the schemas *internals*. The goal is to make `schema/v4/core` as extensible and unopinionated as possible. Other libraries can "build their own Schema" on top of these classes without `schema/v4/core` cluttering up the interface. Refer to the implementations of `schema` and `schema/mini` for examples of how to extend these classes. 

The `_schema` internals property contains some notable properties:

- `.def` — The schema's *definition*: this is the object you pass into the class's constructor to create an instance. It completely describes the schema, and it's JSON-serializable.
  - `.def.type` — A string representing the schema's type, e.g. `"string"`, `"object"`, `"array"`, etc.
  - `.def.checks` — An array of *checks* that are executed by the schema after parsing.
- `.input` — A virtual property that "stores" the schema's *inferred input type*.
- `.output` — A virtual property that "stores" the schema's *inferred output type*.
- `.run()` — The schema's internal parser implementation.

If you are implementing a tool (say, a code generator) that must traverse Schema schemas, you can cast any schema to `$SchemaTypes` and use the `def` property to discriminate between these classes.

```ts
export function walk(_schema: Schema.$SchemaType) {
  const schema = _schema as Schema  .$SchemaTypes;
  const def = Schema._schema.def;
  switch (def.type) {
    case "string": {
      // ...
      break;
    }
    case "object": {
      // ...
      break;
    }
  }
}
```

## Parsing 

As the Schema Core schema classes have no methods, there are top-level functions for parsing data.

```ts
import * as Schema from "schema/v4/core";

const schema = new Schema.$SchemaString({ type: "string" });
Schema.parse(schema, "hello");
Schema.safeParse(schema, "hello");
await Schema.parseAsync(schema, "hello");
await Schema.safeParseAsync(schema, "hello");
```


## Checks

Every Schema schema contains an array of *checks*. These perform post-parsing refinements (and occasionally mutations) that *do not affect* the inferred type.

```ts
const schema = Schema.string().check(Schema.email()).check(Schema.min(5));
// => $SchemaString

Schema._schema.def.checks;
// => [$SchemaCheckEmail, $SchemaCheckMinLength]
```

The base class for all Schema checks is `$SchemaCheck`. It accepts a single generic parameter `T`.

```ts
export class $SchemaCheck<in T = unknown> {
  _schema: { /* internals */}
}
```

The `_schema` internals property contains some notable properties:

- `.def` — The check's *definition*: this is the object you pass into the class's constructor to create the check. It completely describes the check, and it's JSON-serializable.
  - `.def.check` — A string representing the check's type, e.g. `"min_length"`, `"less_than"`, `"string_format"`, etc.
- `.check()` — Contains the check's validation logic.

`schema/v4/core` exports a number of subclasses that perform some common refinements. All first-party subclasses are exported as a union called `Schema.$SchemaChecks`.

```ts
export type $SchemaChecks =
  | $SchemaCheckLessThan
  | $SchemaCheckGreaterThan
  | $SchemaCheckMultipleOf
  | $SchemaCheckNumberFormat
  | $SchemaCheckBigIntFormat
  | $SchemaCheckMaxSize
  | $SchemaCheckMinSize
  | $SchemaCheckSizeEquals
  | $SchemaCheckMaxLength
  | $SchemaCheckMinLength
  | $SchemaCheckLengthEquals
  | $SchemaCheckProperty
  | $SchemaCheckMimeType
  | $SchemaCheckOverwrite
  | $SchemaCheckStringFormat
```


You can use the `._schema.def.check` property to discriminate between these classes.

```ts
const check = {} as Schema  .$SchemaChecks;
const def = check._schema.def;

switch (def.check) {
  case "less_than":
  case "greater_than":
    // ...
    break;
}
```


As with schema types, there are a number of subclasses of `$SchemaCheckStringFormat` that implement various *string formats*. 

```ts
export type $SchemaStringFormatChecks =
  | $SchemaCheckRegex
  | $SchemaCheckLowerCase
  | $SchemaCheckUpperCase
  | $SchemaCheckIncludes

  | $SchemaGUID
  | $SchemaUUID
  | $SchemaEmail
  | $SchemaURL
  | $SchemaEmoji
  | $SchemaNanoID
  | $SchemaCUID
  | $SchemaCUID2
  | $SchemaULID
  | $SchemaXID
  | $SchemaKSUID
  | $SchemaISODateTime
  | $SchemaISODate
  | $SchemaISOTime
  | $SchemaISODuration
  | $SchemaIPv4
  | $SchemaIPv6
  | $SchemaCIDRv4
  | $SchemaCIDRv6
  | $SchemaBase64
  | $SchemaBase64URL
  | $SchemaE164
  | $SchemaJWT;
```


Use a nested `switch` to discriminate between the different string format checks.

```ts
const check = {} as Schema  .$SchemaChecks;
const def = check._schema.def;

switch (def.check) {
  case "less_than":
  case "greater_than":
  // ...
  case "string_format":
    {
      const formatCheck = check as Schema  .$SchemaStringFormatChecks;
      const formatCheckDef = formatCheck._schema.def;

      switch (formatCheckDef.format) {
        case "email":
        case "url":
          // do stuff
      }
    }
    break;
}
```

You'll notice some of these string format *checks* overlap with the string format *types* above. That's because these classes implement both the `$SchemaCheck` and `$SchemaType` interfaces. That is, they can be used as either a check or a type. In these cases, both `._schema.parse` (the schema parser) and `._schema.check` (the check validation) are executed during parsing. In effect, the instance is prepended to its own `checks` array (though it won't actually exist in `._schema.def.checks`).

```ts
// as a type
Schema.email().parse("user@example.com");

// as a check
Schema.string().check(Schema.email()).parse("user@example.com")
```

## Errors

The base class for all errors in Schema is `$SchemaError`.

> For performance reasons, `$SchemaError` *does not* extend the built-in `Error` class! So using `instanceof Error` will return `false`.

- The `schema` package implements a subclass of `$SchemaError` called `SchemaError` with some additional convenience methods.
- The `schema/mini` sub-package directly uses `$SchemaError`

```ts
export class $SchemaError<T = unknown> implements Error {
 public issues: $SchemaIssue[];
}
```

## Issues

The `issues` property corresponds to an array of `$SchemaIssue` objects. All issues extend the `Schema.$SchemaIssueBase` interface.

```ts
export interface $SchemaIssueBase {
  readonly code?: string;
  readonly input?: unknown;
  readonly path: PropertyKey[];
  readonly message: string;
}
```

Schema defines the following issue subtypes:

```ts
export type $SchemaIssue =
  | $SchemaIssueInvalidType
  | $SchemaIssueTooBig
  | $SchemaIssueTooSmall
  | $SchemaIssueInvalidStringFormat
  | $SchemaIssueNotMultipleOf
  | $SchemaIssueUnrecognizedKeys
  | $SchemaIssueInvalidUnion
  | $SchemaIssueInvalidKey
  | $SchemaIssueInvalidElement
  | $SchemaIssueInvalidValue
  | $SchemaIssueCustom;
  ```

For details on each type, refer to [the implementation](https://github.com/colinhacks/schema/blob/main/packages/schema/src/v4/core/errors.ts).
