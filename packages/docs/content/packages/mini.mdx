Schema Mini is a tree-shakable variant of Schema. To try it:

```sh
npm install schema@^4.0.0
```

To import it:

```ts
import * as Schema from "schema/mini";
```

The same API is published as a standalone package, `@schema/mini`, that re-exports `schema/mini` from a peer dependency on `schema`. Its version tracks `schema`.

```sh
npm install schema @schema/mini
```

```ts
import * as Schema from "@schema/mini";
```

Schema Mini implements the exact same functionality as `schema`, but using a *functional*, *tree-shakable* API. If you're coming from `schema`, this means you generally will use *functions* in place of methods.

```ts
// regular Schema
const mySchema = Schema.string().optional().nullable();

// Schema Mini
const mySchema = Schema.nullable(Schema.optional(Schema.string()));
```

## Tree-shaking

Tree-shaking is a technique used by modern bundlers to remove unused code from the final bundle. It's also referred to as *dead-code elimination*.

In regular Schema, schemas provide a range of convenience methods to perform some common operations (e.g. `.min()` on string schemas). Bundlers are generally not able to remove ("treeshake") unused method implementations from your bundle, but they are able to remove unused top-level functions. As such, the API of Schema Mini uses more functions than methods.

```ts
// regular Schema
Schema.string().min(5).max(10).trim()

// Schema Mini
Schema.string().check(Schema.minLength(5), Schema.maxLength(10), Schema.trim());
```

To give a general idea about the bundle size reduction, consider this simple script:

```ts
Schema.boolean().parse(true)
```

Bundling this with Schema and Schema Mini results in the following bundle sizes. Schema Mini results in a 64% reduction.

| Package | Bundle size (gzip) |
|---------|-------------|
| Schema Mini | `2.12kb` |
| Schema | `5.91kb` |

With a marginally more complex schema that involves object types:

```ts
const schema = Schema.object({ a: Schema.string(), b: Schema.number(), c: Schema.boolean() });

Schema.parse({
  a: "asdf",
  b: 123,
  c: true,
});
```

| Package | Bundle size (gzip) |
|---------|-------------|
| Schema Mini | `4.0kb` |
| Schema | `13.1kb` |

This gives you a sense of the bundle sizes involved. Look closely at these numbers and run your own benchmarks to determine if using Schema Mini is worth it for your use case.

## When (not) to use Schema Mini

In general you should probably use regular Schema unless you have uncommonly strict constraints around bundle size. Many developers massively overestimate the importance of bundle size to application performance. In practice, bundle size on the scale of Schema (`5-10kb` typically) is only a meaningful concern when optimizing front-end bundles for a user base with slow mobile network connections in rural or developing areas. 

Let's run through some considerations:

### DX

The API of Schema Mini is more verbose and less discoverable. The methods in Schema's API are much easier to discover & autocomplete through Intellisense than the top-level functions in Schema Mini. It isn't possible to quickly build a schema with chained APIs. (Speaking as the creator of Schema: I spent a lot of time designing the Schema Mini API to be as ergonomic as possible, but I still have a strong preference the standard Schema API.)

### Backend development

If you are using Schema on the backend, bundle size on the scale of Schema is not meaningful. This is true even in resource-constrained environments like Lambda. [This post](https://medium.com/@adtanasa/size-is-almost-all-that-matters-for-optimizing-aws-lambda-cold-starts-cad54f65cbb) benchmarks cold start times with bundles of various sizes. Here is a subset of the results:

| Bundle size | Lambda cold start time |
|-------------|----------------|
| `1kb` | `171ms` |
| `17kb` (size of gzipped non-Mini Schema) | `171.6ms` (interpolated) |
| `128kb` | `176ms` |
| `256kb` | `182ms` |
| `512kb` | `279ms` |
| `1mb` | `557ms` |

The minimum cold start time for a negligible `1kb` bundle is `171ms`. The next bundle size tested is `128kb`, which added only `5ms`. When gzipped, the bundle size for the entirely of regular Schema is roughly `17kb`, which would correspond to a `0.6ms` increase in startup time. 

### Internet speed

Generally, the round trip time to the server (`100-200ms`) will dwarf the time required to download an additional `10kb`. Only on slow 3G connections (sub-`1Mbps`) does the download time for an additional `10kb` become more significant. If you aren't optimizing specifically for users in rural or developing areas, your time is likely better spent optimizing something else.

## `SchemaMiniType`

All Schema Mini schemas extend the `Schema.SchemaMiniType` base class, which in turn extends `Schema.core.$SchemaType` from [`schema/v4/core`](/packages/core). While this class implements far fewer methods than `SchemaType` in `schema`, some particularly useful methods remain.


### `.parse`

This is an obvious one. All Schema Mini schemas implement the same parsing methods as `schema`.

```ts
import * as Schema from "schema/mini"

const mySchema = Schema.string();

mySchema.parse('asdf')
await mySchema.parseAsync('asdf')
mySchema.safeParse('asdf')
await mySchema.safeParseAsync('asdf')
```

### `.check()`

In regular Schema there are dedicated methods on schema subclasses for performing common checks:

```ts
import * as Schema   from "schema";

Schema.string()
  .min(5)
  .max(10)
  .refine(val => val.includes("@"))
  .trim()
```

In Schema Mini such methods aren't implemented. Instead you pass these checks into schemas using the `.check()` method:

```ts
import * as Schema from "schema/mini"

Schema.string().check(
  Schema.minLength(5), 
  Schema.maxLength(10),
  Schema.refine(val => val.includes("@")),
  Schema.trim()
);
```

The following checks are implemented. Some of these checks only apply to schemas of certain types (e.g. strings or numbers). The APIs are all type-safe; TypeScript won't let you add an unsupported check to your Schema.

```ts
Schema.lt(value);
Schema.lte(value); // alias: Schema.maximum()
Schema.gt(value);
Schema.gte(value); // alias: Schema.minimum()
Schema.positive();
Schema.negative();
Schema.nonpositive();
Schema.nonnegative();
Schema.multipleOf(value);
Schema.maxSize(value);
Schema.minSize(value);
Schema.size(value);
Schema.maxLength(value);
Schema.minLength(value);
Schema.length(value);
Schema.regex(regex);
Schema.lowercase();
Schema.uppercase();
Schema.includes(value);
Schema.startsWith(value);
Schema.endsWith(value);
Schema.property(key, schema);
Schema.mime(value);

// custom checks
Schema.refine()
Schema.check()   // replaces .superRefine()

// mutations (these do not change the inferred types)
Schema.overwrite(value => newValue);
Schema.normalize();
Schema.trim();
Schema.toLowerCase();
Schema.toUpperCase();

// metadata (registers schema in Schema.globalRegistry)
Schema.meta({ title: "...", description: "..." });
Schema.describe("...");
```

### `.register()`

For registering a schema in a [registry](/metadata#registries).

```ts
const myReg = Schema.registry<{title: string}>();

Schema.string().register(myReg, { title: "My cool string schema" });
```

### `.brand()`

For *branding* a Schema. Refer to the [Branded types](/api#branded-types) docs for more information.

```ts
import * as Schema from "schema/mini"

const USD = Schema.string().brand("USD");
```


### `.clone(def)`

Returns an identical clone of the current schema using the provided `def`.

```ts
const mySchema = Schema.string()

mySchema.clone(mySchema._schema.def);
```

## No default locale

While regular Schema automatically loads the English (`en`) locale, Schema Mini does not. This reduces the bundle size in scenarios where error messages are unnecessary, localized to a non-English language, or otherwise customized.

This means, by default the `message` property of all issues will simply read `"Invalid input"`. To load the English locale:

```ts
import * as Schema from "schema/mini"
import { en } from "schema/locales";

Schema.config(en());
```

Refer to the [Locales](/error-customization#internationalization) docs for more on localization.
